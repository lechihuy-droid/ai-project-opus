Kết luận: Orchestration của Hermes là work-queue/blackboard cổ điển làm rất tốt phần vận hành (durability, recovery, audit) chứ không phải "swarm thông minh" — điểm 7.5/10. Giá trị với ta: 3 pattern đáng mượn (mục 4) mà không cần chạy Hermes.

1. Mô hình orchestration — Kanban board

Hermes có 2 cơ chế song song: delegate_task (blocking, subagent vô danh, cho việc ngắn) và Kanban (fire-and-forget work queue, cho việc dài/batch). Kanban là phần đáng phân tích:

Điểm mạnh / điểm yếu

Mạnh
  • Durability là first-class: crash recovery, retry, resume, audit — chính là những thứ in-process crew (kiểu CrewAI trong crews/ của ta) không có, và là lý do loại kiến trúc đó mong manh với việc dài.
  • OS-process isolation per worker: đơn giản, dễ debug, không chia sẻ state ngầm.
  • Verifier gate trong swarm topology: kết quả worker phải qua kiểm chứng trước khi tổng hợp.
  • Structured handoff (metadata + summary) — downstream không phải parse văn xuôi.
Yếu
  • Single-host by design: SQLite local, không cross-host; mọi profile chạy cùng UID — một worker bị poison đọc/ghi được board của tất cả (threat model yếu).
  • Decomposition = LLM đoán, không đo chất lượng phân rã — sai từ gốc thì verifier cuối không cứu được chi phí đã đốt.
  • Polling 60s + spawn process: latency cao, không cho interactive multi-agent.
  • Flow control kém hơn explicit DAG/state-machine (kiểu LangGraph) — không định nghĩa được conditional branching phức tạp ngoài dependency link.

Định vị: giữa hai cực — hơn CrewAI-style crew về durability/ops, kém LangGraph-style về kiểm soát flow. Chỗ đứng của nó: batch automation dài hơi trên một máy, đúng use-case "personal agent chạy nền".

2. Loop engineering — hai vòng lặp

2a. Vòng online (trong runtime)

  • Trigger: task ≥5 tool calls → tự sinh SKILL.md. Heuristic thô — sẽ "bất tử hóa" cả workflow chỉ dùng một lần (chính docs thừa nhận).
  • Self-patch khi dùng: gặp thông tin mâu thuẫn/mở rộng → sửa skill tại chỗ. Nhanh, nhưng một bản patch tồi làm suy giảm âm thầm skill đang dựa vào — failure mode là drift hành vi tinh vi, không phải crash.
  • Nudge memory: agent tự nhắc mình persist kiến thức định kỳ; session search FTS5 (từ v2026.5.28 không tốn LLM).
  • Curator (từ v0.12): tự grade, gộp, tỉa skill chu kỳ 7 ngày — đây là câu trả lời cho drift, cùng pattern với wiki lint ta từng chạy. Nhưng grade bằng LLM-judge, không phải eval khách quan.
  • Benchmark "nhanh hơn 40% với skill tự tạo" là self-reported của Nous — chưa có kiểm chứng độc lập.

2b. Vòng offline (hermes-agent-self-evolution)

Repo riêng, tách khỏi runtime: DSPy + GEPA (Genetic-Pareto reflective prompt evolution) đọc execution traces → hiểu nguyên nhân fail → sinh biến thể skill/prompt → đánh giá theo ràng buộc → chọn → mở PR cho người review. Không train weights, chi phí $2–10/lần chạy. Trạng thái: Phase 1 (tối ưu SKILL.md) xong; tool descriptions, system prompt, code evolution (Darwinian Evolver, git-based organisms) mới ở roadmap.

Lỗ hổng chung của loop: thiếu chữ "measure"

Vòng online có create → use → patch → curate nhưng không có eval hồi quy: không gì xác nhận skill sau khi patch còn tốt như trước. Phê bình "your agent has no performance review" là đúng. Vòng offline có đo (test + GEPA fitness) nhưng chạy ngoài băng, thủ công. Cộng thêm skill poisoning (đã phân tích ở EVAL trước): loop biến một lần prompt injection thành thỏa hiệp vĩnh viễn — Promptware defense (v2026.5.28) là giảm nhẹ, chưa phải lời giải.

4. Ba pattern đáng mượn cho workspace của ta (không cần Hermes)

1 — Skill-as-markdown + Curator chu kỳ

Learning = context engineering: kinh nghiệm đọng thành file văn bản diff được, rollback được. Ta đã có mầm này (lessons/, self-improvement loop trong CLAUDE.md). Bổ sung phần Hermes làm tốt hơn: chu kỳ curate định kỳ — grade/gộp/tỉa lessons + Claude Code skills, thay vì chỉ append.

Áp dụng được ngay

2 — Durable queue + heartbeat + verifier gate

Nếu sau này cần multi-agent thật (Lucida pipeline, metagpt-ai-company), mượn kiến trúc Kanban: board SQLite + event log bất biến + heartbeat/reclaim + verifier gate trước synthesizer — thay vì in-process crew kiểu CrewAI (đã thấy mong manh ở Module A cũ).

Khi có nhu cầu multi-agent

3 — Tự cải tiến qua PR + test gate

Mô hình vòng offline đáng sao chép nguyên tắc: mọi thay đổi tự động vào prompt/skill phải đi qua biến thể → test → human review → merge, không bao giờ tự ghi đè trực tiếp. Đây là cách an toàn duy nhất hiện nay để "self-improve".

Nguyên tắc thiết kế

Không đổi kết luận [OPT-3]: phân tích này củng cố No-Go — phần tốt nhất của Hermes (ops durability, loop mechanics) là pattern ta học được, còn phần ta phải gánh nếu chạy nó (security model, drift, runtime thứ hai) thì vẫn nguyên.
