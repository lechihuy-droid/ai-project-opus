Build mới "Hermes" hoàn toàn — nên hay không?

Bản so sánh 3 con đường cho 4 năng lực bạn muốn · pre-RD, để quyết định

2026-06-13 · Tuyến Opus · Tiếp nối 2 bản EVAL Hermes trước

Khuyến nghị một dòng: KHÔNG build mới hoàn toàn. Dựng dần (incremental) trên nền Claude Code sẵn có. Bạn muốn cả 4 năng lực, nhưng nền hiện tại đã lấp 2 cái gần xong và 2 cái còn lại là lớp glue ~vài trăm dòng, không phải runtime mới. Tự build từ số 0 cả 4 = tái phát minh Hermes với ít người soi hơn; dùng Hermes thật = đã No-Go vì trùng vai trò interface. Con đường thứ ba thắng cả hai.

1. Ba con đường — khung quyết định

A — Build mới hoàn toàn

Tự viết runtime riêng: gateway, skill engine, memory store, orchestrator, loop. Độc lập Claude Code.

Effort tháng–quý · rủi ro cao

B — Dùng Hermes sẵn

Cài NousResearch/hermes-agent, viết SKILL.md gọi pipeline.

Đã No-Go (EVAL #1)

C — Dựng dần trên Claude Code

Lấy 4 năng lực, map lên thứ đã có; chỉ build phần còn thiếu dưới dạng glue mỏng + quy trình.

Khuyến nghị · effort ngày

Vì sao A sai cho bối cảnh 1 người: giá trị của một agent runtime nằm ở phần "chán" — gateway đa nền tảng, recovery, sandbox, MCP, 19.900 skill catalog. Bạn không dùng phần lớn trong đó, và viết lại phần bạn có dùng thì thừa hưởng nguyên các lỗ hổng đã phân tích (skill poisoning, drift, security cùng UID) mà không có cộng đồng vá. Build mới chỉ hợp lý khi bạn có nhu cầu mà cả Claude Code lẫn Hermes đều không đáp ứng — hiện chưa có (xem mục 4).

2. Bốn năng lực bạn muốn — bạn đã có bao nhiêu?

Đây là phần quan trọng nhất của quyết định. Với mỗi năng lực: Claude Code/workspace đã cho gì, khoảng cách thật, và nên build hay không.

Năng lựcĐã có trên nền hiện tạiKhoảng cách thậtPhán quyết
Skill tự tích lũy Claude Code skills = markdown đúng chuẩn agentskills.io (cùng chuẩn Hermes dùng). Có lessons/ + self-improvement loop trong CLAUDE.md. Thiếu auto-distill (tự đúc skill sau task) + curator chu kỳ (grade/gộp/tỉa). Glue nhỏ Hook + 1 lệnh curate định kỳ. Không cần runtime.
Trí nhớ bền cross-session personal-wiki/ chính là long-term memory có cross-ref + traceability — mạnh hơn FTS5 của Hermes về chất lượng. Có ai/handoff-*.md, status.md. Memory hiện thủ công (bạn gọi ingest). Thiếu: index session/handoff tự động + recall nhanh khi mở session mới. Điểm yếu thật nhất Đáng làm nhất. Build SQLite FTS index trên ai/sessions/ + wiki. Glue vừa.
Điều phối nhiều agent Claude Code có Agent/subagent tool (fan-out song song, isolation worktree) — đang dùng ngay trong session này. Subagent là in-process, ephemeral: không durable, không retry/resume qua crash, không verifier gate chính thức. Tùy nhu cầu Đa số việc của bạn subagent đủ. Chỉ build durable queue (pattern Kanban) khi có job dài thật (Lucida render).
Tự cải tiến an toàn Có git + test có thể chạy. Có thói quen review qua PR (đang dùng branch này). Chưa có vòng variant → test → review → merge tự động cho prompt/skill. Làm cuối, thận trọng Rủi ro cao nhất (drift/poisoning). Là quy trình + ít automation, human gate bắt buộc.
Phát hiện then chốt: 2/4 năng lực (skill, trí nhớ) bạn đã có nền tốt hơn Hermes — personal-wiki là knowledge graph thật, hơn hẳn skill-markdown phẳng. Cái bạn thiếu không phải "khả năng" mà là tự động hóa mấy thứ đang làm tay. Đó là lý do build mới hoàn toàn là sai hướng: bạn sẽ vứt đi tài sản mạnh nhất (wiki) để dựng lại thứ yếu hơn.

3. Nếu chọn C — lộ trình dựng dần theo giá trị/effort

Không làm cùng lúc. Mỗi bước độc lập, có giá trị riêng, dừng được bất cứ lúc nào. Mỗi bước cần RD nhẹ trước khi code (SDD gate).

  • Bước 1 — Trí nhớ bền (giá trị cao nhất)

    Index ai/sessions/ + handoff-*.md + wiki INDEX vào SQLite FTS5. Một lệnh recall "<câu>" trả về ngữ cảnh liên quan khi mở session. Lấp đúng điểm yếu nhất của Claude Code (mỗi session fresh). Verify: hỏi 5 câu về việc tuần trước, so với tự nhớ.

  • Bước 2 — Skill tự tích lũy + curator

    Hook sau task lớn → đề xuất distill thành skill (bạn duyệt, không tự ghi). Lệnh curate chu kỳ: grade/gộp/tỉa lessons/ + skills. Mượn pattern Curator của Hermes nhưng giữ human gate.

  • Bước 3 — Durable orchestration (chỉ khi cần)

    Khi có job dài thật (Lucida video, batch research): SQLite queue + heartbeat + verifier gate trước synthesizer. Trước đó cứ dùng subagent. Trigger: có việc >30 phút cần chạy nền + retry.

  • Bước 4 — Tự cải tiến có gate (làm sau cùng)

    Vòng variant → test → PR → human merge cho prompt/skill. Không tự ghi đè bao giờ. Chỉ làm khi 3 bước trên ổn định.

Tổng nếu làm cả 4 bước: ước lượng 5–8 ngày rải nhiều tuần — so với hàng tháng cho con đường A, và ra một hệ của riêng bạn, không phải runtime thứ hai phải nuôi.

4. Khi nào "build mới hoàn toàn" mới thực sự hợp lý?

Để công bằng với phương án A — nó đúng nếu (và chỉ nếu) có một trong các điều kiện sau, mà hiện bạn chưa có:

Điều kiện kích hoạt ABạn có chưa?
Cần chạy độc lập hoàn toàn khỏi Claude Code (vendor lock-in là vấn đề thật)Chưa — đang hài lòng với Claude Code
Cần multi-host / nhiều máy phối hợp (Hermes single-host không đủ)Chưa — chạy 1 máy Windows
Muốn học sâu bằng cách tự xây (mục tiêu giáo dục, không phải sản phẩm)Nếu đây là mục tiêu thật thì A hợp lý — nhưng scope nhỏ lại, làm 1 năng lực để học
Có nhu cầu cụ thể cả Claude Code lẫn Hermes đều không làm đượcChưa nêu được nhu cầu nào như vậy
Nếu động cơ là "muốn tự xây để hiểu/làm chủ" (chính đáng) — thì vẫn không build cả 4 cùng lúc. Chọn Bước 1 (trí nhớ) làm theo cách tự viết từ đầu: vừa học kiến trúc, vừa ra thứ dùng được, vừa không khóa mình vào dự án khổng lồ. Đó là cách "build mới" khôn ngoan.

5. Tóm tắt quyết định

Nên
  • Đi con đường C — dựng dần trên Claude Code.
  • Bắt đầu Bước 1 (trí nhớ bền) — giá trị cao nhất, lấp điểm yếu thật.
  • Giữ personal-wiki/ làm brain — tài sản mạnh nhất.
  • Mỗi bước: RD nhẹ → build → verify, dừng được.
Không nên
  • Build cả 4 năng lực từ số 0 thành một runtime mới.
  • Vứt wiki để dựng lại skill-store phẳng kiểu Hermes.
  • Làm phần tự-cải-tiến trước khi có trí nhớ + skill ổn.
  • Fork Hermes.

Việc tiếp theo cần bạn quyết: xác nhận đi con đường C + Bước 1, để tôi viết RD-cross-session-memory.md (SDD gate 1). Hoặc nếu động cơ thật là "tự xây để học", nói rõ — tôi điều chỉnh lộ trình theo hướng giáo dục thay vì tối-ưu-effort.
