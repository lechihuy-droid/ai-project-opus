Một kế hoạch duy nhất cho 4 năng lực bạn muốn — xây trên Claude-native, mượn pattern Hermes, chạy trên subscription

Hai phân tích độc lập, một kết luận: nhánh Hermes-eval (bắt đầu từ "có nên tích hợp/build Hermes?") và báo cáo multi-agent architecture (bắt đầu từ "có nên thêm framework multi-agent?") gặp nhau ở cùng một câu trả lời — đừng thêm runtime/framework ngoài; formalize cái đã có thành Claude-native (Skills + Subagents + Hooks + MCP) và nâng gateway lên Claude Agent SDK. Báo cáo trả lời "dùng công cụ gì"; nhánh Hermes trả lời "mượn pattern nào để hệ tự tốt lên mà không drift". Ghép lại thành kế hoạch dưới đây.

Đây là chỗ hai tài liệu ghép chặt nhất: mỗi năng lực = một primitive Claude-native (báo cáo) + một pattern mượn từ Hermes (EVAL) + phần nền bạn đã có.

Cả hai phân tích đều cảnh báo cùng một cám dỗ cần tránh: kéo hạ tầng nặng (vector DB, message queue, framework đa agent, runtime thứ hai) vào một bài toán single-user.

3. Kiến trúc hợp nhất — orchestrator-worker

So với sơ đồ trong báo cáo gốc: thêm 2 thành phần từ nhánh Hermes — Hooks làm gate cứng (chống skill poisoning + ép Karpathy invariant "chỉ wiki_ops ghi wiki") và vòng self-improve có test gate (chống drift mà Hermes vướng). Đây chính là 2 lỗ hổng lớn nhất của Hermes được bịt ngay từ thiết kế.

Mô hình hai lớp — Claude điều phối, Codex thực thi

Tách bạch hai vai "Claude" từng gây lẫn: nay chỉ còn một lớp Claude ở vị trí điều phối (Claude Code tương tác, Opus/Sonnet), và Codex (codex exec) là tác nhân thực thi headless cho cả hai loại việc — build (viết code + test từ BD) và runtime (vận hành pipeline: synthesis / filter / ingest / curator). Đây là quyết định mở rộng vai Codex: nó thay claude -p làm runtime operator trong utils/llm.py, không chỉ làm coding như routing cũ.

Phân vai: Lớp 1 (Claude) nghĩ — plan, RD/SD/BD, kiến trúc, review, quyết định; không tự code, không tự chạy pipeline. Lớp 2 (Codex) làm — mọi thực thi không người trông: nhận BD từ Claude (build) hoặc trigger từ Task Scheduler (runtime), rồi ghi kết quả vào raw/ + wiki.

Hệ quả phải biết khi chọn hướng này:
  • Mất credit subscription cho lớp runtime. Codex là agent của OpenAI, không chạy trên credit Agent SDK 15/6 của Claude. Đưa runtime operator sang Codex tức là đảo lại chính ràng buộc "không phụ thuộc API key trả phí riêng" — lớp runtime giờ tính tiền theo OpenAI/Codex, không còn nằm trong subscription Claude.
  • Codex là coding agent. Dùng cho tác vụ suy-luận-trên-văn-bản (lọc article, viết brief) là phi truyền thống — phải đo chất lượng synthesis ở pilot trước khi thay toàn bộ.
  • Doc-sync: hai quy tắc CLAUDE.md cần cập nhật khi triển khai — "mọi LLM call dùng Claude CLI" và "Codex chỉ coding". Quyết định này cũng thay nội dung Phase 3 (runtime operator: Agent SDK/claude -p → Codex).

4. Lộ trình hợp nhất (gộp 4 bước Hermes-decision + 5 bước báo cáo)

Hai lộ trình trùng nhau nhiều — gộp thành một chuỗi tăng dần, mỗi phase độc lập, dừng được, cần RD nhẹ trước khi code (SDD gate).

  • Phase 0 — Giữ nguyên

    Pipeline đang chạy ổn. KHÔNG refactor big-bang. Mọi thay đổi surgical theo Karpathy principles.

  • Phase 1 — Nền: Skills + Trí nhớ (giá trị cao nhất, rẻ nhất)

    (a) Viết SKILL.md cho 3 pipeline cốt lõi (collector, synthesizer, wiki-curator) — chuẩn hoá script rời thành skill versioned, không đổi runtime. (b) Build recall: index ai/sessions/ + handoff-*.md + wiki INDEX vào SQLite FTS5. Lấp đúng điểm yếu nhất (mỗi session fresh). Đây là giao điểm "Bước 1 Skills" của báo cáo + "Bước 1 trí nhớ" của decision doc.

  • Phase 2 — Hooks (gate cứng) + Curator

    Hook PreToolUse chặn ghi raw/; SessionStart auto-load ai/status.md; audit log mọi tool call. Thêm lệnh curate chu kỳ grade/gộp/tỉa lessons/ + skills (pattern Curator Hermes, giữ human gate). Biến luật mềm trong CLAUDE.md thành ràng buộc deterministic.

  • Phase 3 — Pilot Codex làm runtime operator (thay claude -p)

    Chọn MỘT pipeline ít rủi ro (weekly synthesizer). Cho codex exec đảm nhận lời gọi trong utils/llm.py thay claude_cli() shell-out. Đo: chất lượng synthesis có giữ được không (Codex vốn là coding agent), error-handling có sạch hơn không, và chi phí Codex/OpenAI ra sao (lớp này không còn nằm trong credit subscription Claude). Đây là feature >20 dòng → cần RD→SD→BD approve.

  • Phase 4 — MCP hoá I/O + Durable queue (khi cần)

    Bọc Telegram + SQLite + Obsidian thành MCP server, tái dùng across pipelines. Chỉ thêm durable queue (SQLite + heartbeat + verifier gate, pattern Kanban) khi xuất hiện job dài thật (vd Lucida render >30 phút cần retry) — trước đó subagent đủ.

  • Phase 5 — Self-improve có gate + dọn legacy

    Vòng variant → test → PR → human merge cho prompt/skill (không bao giờ tự ghi đè — bài học drift/poisoning của Hermes). Gỡ hẳn CrewAI crews/ sau khi pilot chứng minh. Làm sau cùng, rủi ro cao nhất.

5. Danh sách "không làm" (hợp nhất cả hai tài liệu)

Từ nhánh Hermes
  • Không build runtime mới từ số 0 cho cả 4 năng lực.
  • Không cho agent tự ghi đè skill (chống drift/poisoning).
  • Không vứt personal-wiki/ để dựng skill-store phẳng.
  • Không fork Hermes; không dùng hermes-agent-self-evolution giai đoạn này.
Từ báo cáo multi-agent
  • Không thêm LangGraph/CrewAI/AutoGen/MetaGPT (buộc API key trả phí).
  • Không adopt nguyên claude-flow/SuperClaude (overkill cho 1 người).
  • Không kéo vector DB / mem0 / Letta ở quy mô single-user.
  • Tham khảo anthropics/skills + awesome-list để copy mẫu lẻ, không adopt cả bộ.

6. Tóm tắt & việc tiếp theo

Câu hỏi gốc "build mới Hermes hoàn toàn được không" → được nhưng không nên; và bây giờ thậm chí không cần: credit Agent SDK 15/6 biến Claude-native + Agent SDK thành nền chạy-trên-subscription cho cả 4 năng lực, còn pattern Hermes (Curator, durable queue, self-improve có test gate) lấp đúng 3 chỗ Claude-native chưa có sẵn — mà không phải gánh runtime thứ hai hay các lỗ hổng của Hermes.
