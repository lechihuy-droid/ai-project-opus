Local web app system architecture

Opus Home as a local dashboard platform

Browser UI + FastAPI backend + client-side state is the current architecture. The main risk is metric semantics drifting between session history and unique progress. The target state is one contract for stats, one owner per metric type, and explicit labels in the UI.

Runtime Flow

Client
Browser
Opens localhost:8765 and renders shell + iframe surfaces.
Server
FastAPI
Serves HTML, static assets, and API routes from a single local process.
Data
localStorage + JSON
Quiz state, history, weak state, and question bank snapshots live locally.

Current Assessment

Strength
Fast iteration, no remote dependency, low latency, easy to run on the same workstation.
Weakness
Two metric systems are easy to confuse: session history versus unique progress.
Operational Risk
Browser cache can keep old UI bundles alive even after source changes if headers are not strict.

Cross-Tab Improvement Priorities

P0
State contracts
Define owner and source for every metric. Home should consume summaries, not re-derive domain logic.
P1
Navigation depth
Tabs need drill-down paths from summary cards to underlying source, history, artifact, or decision record.
P2
Freshness
Every data-backed tab should show last updated time, source count, and whether it is static or API-backed.
P3
Action model
Each tab needs one primary next action. Otherwise Home becomes a collection of dashboards, not an operating system.

System Map

Shell UI

Opus Home
Navigation, summary cards, and embedded app surfaces.
Owner: Home
  • Reads dashboard snapshot from /api/dashboard
  • Shows separate blocks for session stats and unique progress
  • Should not recompute quiz correctness from the wrong source

Quiz Engine

PMP Quiz
Standalone router, renderer, storage, and weak mode logic.
Owner: Quiz
  • Owns session history derivation
  • Owns unique seen/wrong sets
  • Exports explicit stats fields, not implicit guesses

Persistence

localStorage
Client-side persistence for history, weak state, and progress.
Risk
  • Needs schema versioning
  • Needs repair / migration logic
  • Should separate session and unique contracts physically

Delivery

FastAPI Static Host
One local process mounts both the home shell and the quiz app.
Stable
  • Must send no-cache headers
  • Should expose consistent asset paths
  • Should avoid mixed bundle ownership

Action Items

New Action: Add a Stats Contract View
Create a small debug panel in Home that prints the exact source for each metric: sessionAnswered, sessionCorrect, uniqueSeenCount, uniqueWrongCount. That makes semantic drift visible before it reaches the user.
Recommended SA: Metric Contract Steward
A dedicated architecture owner for stats semantics across Home, PMP, and weak mode. This role owns the vocabulary, the storage schema, the migration path, and the UI labels for all counters.

Decision Matrix

Architecture fit
7.5 / 10
Good for a local personal dashboard. Not yet ideal for highly reliable stats without a stronger contract layer.
Main defect
Semantics drift
The same labels were used for both session totals and unique progress, which created the false impression that counts were wrong.
Best next move
Separate ownership
Keep session history, unique progress, and weak progress as explicit, separate outputs everywhere.
