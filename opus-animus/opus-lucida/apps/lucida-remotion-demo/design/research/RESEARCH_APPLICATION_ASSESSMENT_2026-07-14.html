1. Kết luận chính

  1. Research đúng về boundary: Git/package là canonical source; generated JSON phục vụ runtime; SQLite chỉ là projection có thể xóa và rebuild.
  2. Research đúng khi hoãn vector: catalog hiện chỉ có 9 style package, 28 template mappings và 7 motion presets. Bottleneck là domain model/capability, không phải tốc độ semantic search.
  3. Storage research chưa mô tả một RAG database hoàn chỉnh: schema chỉ index component/template entity, chưa có source snapshot, document, chunk, observation, asset và evaluation query.
  4. Hai source of truth đang xung đột: design/knowledge/ARCHITECTURE.md vẫn gọi PostgreSQL + pgvector là MVP; research mới chuyển sang local-first SQLite. Phải cập nhật architecture decision trước implementation.
  5. Điều kiện Phase 0 chưa đạt: glitch-text vẫn map về HeroTitleAdapter; chưa có design/template-library, knowledge compiler hoặc generated template index.
  6. Audio đã có plumbing nhưng bằng chứng E2E chưa kín: script test yêu cầu --run-id; chạy package script mặc định chỉ báo usage và fail, nên chưa thể coi Audio Foundation đã fully verified.

3. Database RAG: scope đúng

Không nên gọi một bảng knowledge_fts là toàn bộ RAG database. Lucida cần hai corpus cùng nằm trong một SQLite projection nhưng có lifecycle khác nhau.

Corpus A: Production Knowledge
style, component, template, motion, transition, capability, compatibility, validation
→
KnowledgeRepository
hard filters, FTS5/BM25, capability scoring, continuity rerank, reasons
→
Director / Tooling
chọn template và asset; renderer chỉ đọc generated JSON đã resolve
Corpus B: Reference Evidence
repository, web, image, theme, source snapshot, document/chunk, observation, rights
→
Candidate Builder
retrieval để nghiên cứu, dedupe và đề xuất; không tự publish
→
Review Gate
approved candidate mới trở thành canonical package trong Git

Boundary: Corpus B không được truy cập trực tiếp trong render path. Reference media là evidence, không tự động trở thành production asset hay style.

4. Sửa schema SQLite v0.1

4.1 Những thiếu sót của schema research hiện tại

  • Không khai báo foreign key cho intents, capabilities, provenance và validation artifacts.
  • Không có CHECK, STRICT, unique relation constraints hoặc delete behavior.
  • knowledge_fts là bảng rời, không có content table/triggers hoặc invariant rebuild nên dễ drift và duplicate.
  • Không có retrieval unit cho repository/web/theme: thiếu sources, source_snapshots, documents, chunks.
  • Không có build_id trên projection rows để audit toàn bộ snapshot.
  • source_commit NOT NULL không phù hợp với web/image/local source; cần source_revision theo loại nguồn và checksum bắt buộc.
  • Chưa có policy cho tiếng Việt. FTS5 unicode61 có thể bỏ dấu Latin nhưng không tự map đ → d; cần lưu thêm normalized search text.

4.2 Logical tables đề xuất

projection_builds
schema_versions

canonical_entities       -- style/component/template/motion/transition
entity_capabilities
entity_relations         -- compatibility and provenance links
validation_artifacts
provenance_records

sources                  -- repo/web/image/theme/media
source_snapshots         -- immutable checksum/revision/license snapshot
documents                -- one source file/page/theme/image note
chunks                   -- stable chunk id + raw text + vi_normalized_text
observations             -- extracted evidence, never production by default

search_documents         -- materialized retrieval document with entity/chunk link
search_fts               -- FTS5 external-content index over search_documents

Mỗi row phải có stable ID, schema version, source/package path, content hash và build ID. Build dùng một transaction, rollback khi lỗi, rồi chạy foreign_key_check, FTS integrity check và parity test với generated JSON.

4.3 Retrieval v0.1

query intent
→ normalize Vietnamese text (NFC + accent-folded field + đ/d mapping)
→ hard filters: status, renderable, rights, aspect ratio, safe area, slots
→ FTS5 BM25 candidate retrieval
→ capability + content-fit + continuity scoring in application code
→ return ranked IDs + selected/rejected reasons + provenance
→ renderer consumes resolved generated JSON, never queries SQLite

6. Acceptance criteria cho RAG v0.1

  • Xóa database và rebuild tạo cùng logical rows và cùng manifest hash.
  • Canonical package là input duy nhất cho production entities; không có API sửa canonical entity trong DB.
  • Query hook + code explanation + low density + 9:16 trả đúng glitch-text sau pilot.
  • Query tiếng Việt có dấu và không dấu trả cùng candidate set trong bộ test đã định nghĩa.
  • Reference result luôn trả source snapshot, checksum, source path/URL, license/rights và collector version.
  • Unsupported/catalog-only template bị loại khi renderable=true.
  • SQLite và generated JSON parity cho production queries.
  • Renderer vẫn render khi database bị xóa nhưng generated runtime index còn hợp lệ.
  • Không có embedding dependency, vector extension hoặc network database trong v0.1.

8. Nguồn kỹ thuật chính thức

  • Node.js SQLite API: DatabaseSync, foreign-key option và timeout có sẵn trong runtime hiện tại.
  • SQLite FTS5: tokenizer, external-content table, rebuild và integrity-check.
  • LanceDB hybrid search: vector + FTS cần reranking; metadata prefilter là default.
  • Transformers.js: local feature-extraction khả dụng, nhưng model fit và evaluation vẫn là trách nhiệm của Lucida.

9. Go / No-go

GO: BD-A gồm Wave 0–2. Kế hoạch đã khóa scope app-local, Node >=24.14 <25, stable IDs, chunking, Vietnamese normalization, exact file map và verification commands.

GATED: BD-B gồm Wave 3–6 chỉ mở khi glitch-text đạt 7/7. RAG v0.1 dùng 32 gold queries; hard-filter precision, accent parity, JSON/SQLite parity và provenance completeness phải đạt 100%; Recall@5 ≥ 0.90, MRR ≥ 0.80, nDCG@5 ≥ 0.85.

NO-GO: build database trước component pilot; để director/renderer query SQL trực tiếp; ingest raw reference thành canonical knowledge; triển khai embedding/LanceDB/PostgreSQL mà chưa có gold query benchmark.
