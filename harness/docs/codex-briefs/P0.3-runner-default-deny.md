## Hiện trạng (đã verify bằng đọc code)

`harness/run_harness.py` quảng cáo ở `README.md:75-83` rằng mọi check bị giam trong `{root}`. Thực tế bị vô hiệu hoá bởi 3 chỗ cộng lại:

**1. Dòng 296-297** — allowlist vô điều kiện:
```python
allowed_names = {str(item).lower() for item in _as_list(check.get("allowed_executables"))}
allowed_names.update({"py", "py.exe", "python", "python.exe"})
```
Bất kỳ check nào gọi `python` đều qua tầng kiểm executable, không cần cờ nào.

**2. Dòng 271-280** — `_looks_like_path_argument` chỉ nhận diện chuỗi có drive letter, `./`, `../`, slash, hoặc đuôi trong `PATHLIKE_SUFFIXES`. Code inline sau `-c` không có đặc điểm nào trong số đó → **không bao giờ bị soi containment**.

**3. Dòng 48-72 + 262-268** — `DANGEROUS_COMMAND_TOKENS` match theo word-boundary regex trên token shell. Bắt được `rm`, `del`. Không bắt `shutil.rmtree`, `os.remove`, `pathlib.Path(...).unlink`, `requests`, `urllib`.

Kết quả: `command: ["python", "-c", "<bất kỳ code gì>"]` chạy tự do, đọc/ghi/xoá đường dẫn tuyệt đối bất kỳ, gọi mạng — trong khi `{python}` và `{py311}` chính là token chuẩn của harness.

**Điểm quan trọng:** logic đúng **đã có sẵn** ở dòng 298-311 — nó so `_norm_path(executable_path)` với `safe_external_paths` (gồm `ctx["python"]`, `ctx["py311"]`, `sys.executable`). Dòng 297 chỉ đơn giản làm nhánh đó bị bỏ qua khi executable là tên trần `python`.

## Yêu cầu thay đổi — `harness/run_harness.py`

### 1. Xoá allowlist vô điều kiện
- Xoá dòng 297 (`allowed_names.update({"py", "py.exe", ...})`)
- Interpreter chỉ hợp lệ khi khớp `safe_external_paths` — nhánh dòng 304-311 đã làm đúng việc này
- Hệ quả: suite phải dùng token `{python}` / `{py311}` (đường dẫn tuyệt đối) thay vì chuỗi `"python"` trần. Đây là hành vi mong muốn.

### 2. Chặn code inline
- Thêm hằng cạnh các set hiện có:
  ```python
  INLINE_CODE_FLAGS = {"-c", "-m", "--command"}
  ```
- Trong `_enforce_command_boundary`, sau phần kiểm executable: nếu bất kỳ token nào trong `command[1:]` khớp `INLINE_CODE_FLAGS` và check không có `allow_inline_code` → `raise BoundaryPolicyError(...)` với message nói rõ flag nào và cách cho phép tường minh

### 3. Ghi rõ vai trò của blacklist
- **Giữ** `DANGEROUS_COMMAND_TOKENS` và vòng lặp dòng 315-319
- Thêm comment ngay trên `DANGEROUS_COMMAND_TOKENS`: đây là lớp defense-in-depth thứ cấp, **không** phải cơ chế containment chính; cơ chế chính là allowlist executable + containment đường dẫn. Mục đích comment: chặn agent sau tưởng nhầm nó là gate và đi thêm token vào đó.

### 4. Tách hàm để test được
- `_enforce_command_boundary` và `_looks_like_path_argument` phải gọi được trực tiếp từ test, không cần dựng subprocess. Nếu cần đổi signature nhẹ để test truyền `ctx`/`check` thì làm, giữ tối thiểu.

## Test phải tạo — `harness/tests/test_boundary.py`

Thư mục `harness/tests/` **chưa tồn tại**, tạo mới (kèm `__init__.py` nếu cần cho import).

Case bắt buộc:
1. **`["python", "-c", "import shutil"]` → `BoundaryPolicyError`** ← đây là bypass trong audit, phải là named test case
2. `["python", "-m", "http.server"]` → `BoundaryPolicyError`
3. `[<ctx python path>, "harness/some_script.py"]` → hợp lệ, không raise
4. `["python", "-c", "..."]` **có** `allow_inline_code: true` → không raise
5. `["bash", "-lc", "ls"]` không `allow_shell` → raise
6. `_looks_like_path_argument("import shutil")` → `False` (ghi lại đúng giới hạn của heuristic, để lần sau không ai tưởng nó soi được code)
7. Argument là đường dẫn tuyệt đối ngoài root → raise
8. `["python.exe", ...]` tên trần → raise sau khi xoá dòng 297
